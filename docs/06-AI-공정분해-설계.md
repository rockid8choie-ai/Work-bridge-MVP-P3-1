# AI 공정 분해 — 공정표를 어떻게 만드는가

> Work bridge MVP [P(3-1)] · 작성 2026-10-13 · RFP 3.5(AI 단가 분석) 구현 설계
> 데이터 모델: `ScopeAnalysis`(분석 1건) → `ScopeItem[]`(공정 행: name · description · estimate · rationale)

---

## 0. 전제 — AI는 "맞히는" 게 아니라 "초안을 쓰는" 것이다

이 제품의 주장은 "AI가 공사비를 정확히 산정한다"가 아니다. **"무엇을 할지 항목으로 적고, 전문가가 고치고, 양쪽이 서명한 뒤 시작한다"** 이다.
AI의 역할은 그 항목 목록의 **초안**을 30초 안에 만들어서 건물주가 빈 종이 앞에 앉지 않게 하는 것이다. 정확도는 전문가 수정 단계가 책임진다.

그래서 설계 원칙 세 가지:
1. AI가 공정 이름을 **자유롭게 짓지 못하게** 한다 → 공정 사전(아래 2장)에서 고른다.
2. AI가 금액을 **아무 숫자로 쓰지 못하게** 한다 → 공정별 단가 범위 안에서만, 근거를 반드시 쓴다.
3. 출력은 **구조화 JSON**으로 받고 zod 로 검증한다. 검증 실패 시 규칙 기반 폴백(`model: "rule"`).

## 1. 입력 — AI에 무엇을 주는가

| 입력 | 출처 | 왜 필요한가 |
|---|---|---|
| 프로젝트 제목·설명 | `Project.title/description` | 분해 대상 본문 |
| 카테고리 | `Project.category` (누수·방수 / 전기·조명 / 설비·배관 / 외벽·도장 / 인테리어·목공 / 소방·안전 / 공조·환기) | 공정 사전을 **해당 카테고리로 한정**한다. 변수를 줄이는 첫 장치 |
| 필요 전문분야 | `ProjectSkill[]` | 복합 공사(누수 + 타일) 판별 |
| 예산 (있으면) | `Project.budget` | 참고용. 단가를 예산에 맞추지 말라고 명시한다 |
| **공정 사전** (해당 카테고리분) | 서버 상수 | 선택지 + 단가 범위 + 단위 |

설명이 20자 미만이거나 공사 내용이 아니면(검증 단계) 분석을 거절하고 "어디가, 어떤 증상인지" 추가 입력을 요구한다.

## 2. 공정 사전 — 변수를 가두는 울타리

카테고리별로 **흔한 소액 보수 공정 20~30개**를 미리 정의한다. 각 항목에 단위, 단가 범위, 선행 공정을 둔다.

```ts
// lib/server/scope/dictionary.ts (발췌)
{
  category: "누수·방수",
  items: [
    { code: "WP-01", name: "누수 원인 진단",      unit: "회",  low: 100_000,  high: 300_000,  note: "육안·청음·열화상. 결과에 따라 후속 공정 확정" },
    { code: "WP-02", name: "실리콘·코킹 재시공",   unit: "m",   low: 8_000,    high: 15_000 },
    { code: "WP-03", name: "우레탄 방수 재시공",   unit: "㎡",  low: 35_000,   high: 60_000,  requires: ["WP-01"] },
    { code: "WP-04", name: "배관 교체(급수·배수)", unit: "식",  low: 400_000,  high: 1_200_000 },
    { code: "WP-05", name: "천장·벽체 마감 복구",  unit: "㎡",  low: 50_000,   high: 120_000 },
    { code: "WP-06", name: "타일 철거·재시공",     unit: "㎡",  low: 80_000,   high: 150_000 },
    { code: "WP-07", name: "폐기물 처리",          unit: "식",  low: 100_000,  high: 300_000 },
    ...
  ]
}
```

**단가 범위의 출처.** 국토교통부 **건설공사 표준시장단가**와 한국건설기술연구원 **표준품셈**이 공개돼 있다. 다만 둘 다 공공 공사·대형 기준이라 소액 보수에 그대로 쓰면 낮게 나온다. MVP 에서는 표준품셈의 노무·재료 구성을 참고하고, 공개 견적 플랫폼(숨고·오늘의집 사례 가격)으로 소액 보수 체감가를 보정해 **범위**로 적는다. 정확한 점 추정이 아니라 "이 구간 밖이면 이상하다"를 걸러내는 울타리다.

사전은 코드로 두고(DB 테이블 아님) 버전을 git 으로 관리한다. 2주 MVP 에서 관리 화면까지 만들 이유가 없다.

## 3. 프롬프트 — 무엇을 시키는가

시스템 프롬프트 요지:

```
너는 건물 유지보수 견적 보조원이다. 아래 공정 사전에서만 공정을 고른다.
사전에 없는 작업이 필요하면 code 를 "ETC" 로 하고 name 을 직접 쓰되, 전체 항목의 1/3 을 넘지 않는다.

규칙
1. 첫 공정은 원인이 불확실한 경우 반드시 "진단" 공정이다. 진단 결과에 따라 달라질 공정은 conditional: true 로 표시한다.
2. 각 공정의 estimate 는 사전의 low~high 안에서 정한다. 벗어나야 하면 rationale 에 이유를 쓴다.
3. rationale 에는 (a) 설명문의 어떤 문장에서 이 공정이 필요하다고 판단했는지 (b) 수량 가정 (c) 단가 근거 를 쓴다.
4. 수량을 알 수 없으면 assumptions 에 가정을 적는다 (예: "화장실 천장 약 4㎡ 가정").
5. 예산에 맞추지 않는다. 예산보다 크면 그대로 쓴다.
6. 공정은 시공 순서대로 정렬한다.
7. JSON 만 출력한다.
```

사용자 메시지: 제목, 설명, 카테고리, 전문분야, 예산, 해당 카테고리의 공정 사전(JSON).

## 4. 출력 — 어떤 모양으로 받는가

```ts
// lib/server/scope/schema.ts
const scopeItemOut = z.object({
  code: z.string(),                       // 사전 코드 또는 "ETC"
  name: z.string().min(2).max(40),
  description: z.string().min(10).max(300),
  quantity: z.number().positive(),
  unit: z.string(),
  estimate: z.number().int().min(10_000),
  rationale: z.string().min(20).max(500),
  conditional: z.boolean().default(false), // 진단 결과에 따라 변동
});

const scopeAnalysisOut = z.object({
  items: z.array(scopeItemOut).min(2).max(12),
  assumptions: z.array(z.string()).max(8),
  totalEstimate: z.number().int(),
  confidence: z.enum(["low", "medium", "high"]),
  missingInfo: z.array(z.string()).max(5),  // "층수", "면적" 등 더 물어야 할 것
});
```

**서버 검증 (AI 를 믿지 않는다):**
- `totalEstimate === sum(items.estimate)` 아니면 서버가 재계산해 덮어쓴다.
- 사전 코드인데 `estimate` 가 `quantity × high × 1.5` 를 넘으면 범위 위반 → 해당 항목에 플래그, 리포트에 "확인 필요" 표시.
- `ETC` 비율 1/3 초과 → 재요청 1회, 그래도 실패 → 폴백.
- 파싱·검증 실패 → **규칙 기반 폴백**: 카테고리 사전의 "기본 세트"(진단 + 대표 공정 2~3개)를 중간값으로 채우고 `model: "rule"` 로 저장. 서비스가 멈추지 않는다.

통과하면 `ScopeAnalysis` 1건 + `ScopeItem` N행으로 저장한다. `rationale` 에 수량 가정과 단가 근거가 들어가므로 RFP 3.5.2 "산정 근거"가 행 단위로 남는다.

## 5. 전문가 수정 — 정확도를 책임지는 단계

리포트는 건물주에게 먼저 보이지만, **계약 범위로 확정되는 건 전문가가 고친 뒤**다.

```
건물주: 분석 요청 → 리포트 열람 → "예산 반영"(선택)        ... A-01, A-02
   ↓ 지원자 수락
전문가: 공정표 편집 — 행 추가/삭제/금액·수량 수정, 변경 사유 입력
   ↓
건물주: 수정된 공정표 + 합의 금액 확인 → 동의/거부           ... A-03, A-04
   ↓ 동의
계약서 자동 생성 — scopeSnapshot 에 확정 공정표 사본 고정     ... A-05
```

- 전문가가 고친 행은 `rationale` 앞에 `[전문가 수정] 사유:` 를 붙여 AI 원안과 구분한다. 분쟁 시 "누가 이 항목을 넣었나"가 남는다.
- `Contract.scopeSnapshot` 은 체결 시점의 사본이다. 이후 `ScopeItem` 이 바뀌어도 계약서는 변하지 않는다.
- 각 확정 행이 `Milestone` 1개가 된다(`scopeItemId` 참조). `conditional` 행도 마일스톤이 되되, 진단 승인 후 금액 재확정이 가능하도록 남긴다 → 아래 6장.

## 6. "뜯어보니 다르다" — 변경 합의 (설계만, 구현은 도전 과제)

공사 변수의 대부분은 진단 후 범위가 바뀌는 데서 온다. MVP 범위 밖이지만 ERD 에 자리를 만든다.

```
ScopeChange { id, contractId, milestoneId?, kind: add|remove|amend,
              requestedBy: client|freelancer, beforeJson, afterJson, reason,
              clientAgreedAt?, freelancerAgreedAt? }
```

- 양측 동의 시 마일스톤 추가/금액 수정, 추가 금액은 에스크로 추가 결제.
- `requestedBy` 가 핵심이다. 소비자분쟁해결기준은 "사업자 요청 변경은 소비자 추가 부담 없음, 소비자 요청 변경은 소비자 부담"으로 정한다. **누가 요청했는지가 기록되면 제도가 돈의 귀속을 정해준다.** 이 테이블은 그 기록이다.
- 발표에서 "현장 가서 달라지면?"에 대한 답: "달라지는 걸 막는 게 아니라, 원래 범위 대비 무엇이 누구 요청으로 바뀌었는지 남긴다."

## 7. 심사 질문 예상과 답

| 질문 | 답 |
|---|---|
| 공사는 변수가 너무 많지 않나 | 그래서 범위를 먼저 적는다. 변수가 적은 일에는 이 장치가 필요 없다. 카테고리 한정 + 공정 사전 + 소액(1,500만 미만) 단건 보수로 변수 폭을 줄였고, 나머지는 전문가 수정과 변경 합의 기록으로 처리한다 |
| AI 단가가 틀리면 | 틀린다. 그래서 범위 안에서만 쓰게 하고, 근거를 행마다 남기고, 전문가가 고친 뒤에야 계약이 된다. AI 원안은 빈 종이를 없애는 초안이다 |
| 단가 범위는 어디서 | 표준시장단가·표준품셈 구성 참고 + 소액 보수 체감가 보정. 점 추정이 아니라 이상치 울타리 |
| 전문가가 금액을 부풀리면 | 건물주가 AI 원안과 전문가 수정안을 나란히 보고 동의한다. 수정 사유가 기록된다 |
| LLM 이 죽으면 | 규칙 기반 폴백으로 기본 세트를 채운다. `model: "rule"` 로 표시돼 리포트에 "자동 생성 초안" 안내가 뜬다 |
