## 프롬프트 본문 (여기부터 복사)

발표자료를 만들어줘. 20분 발표 + 5분 질의응답용, 총 20장. 톤은 심사위원 앞 제품 발표: 짧은 문장, 숫자는 크게, 장식 없음. 흰 배경, 짙은 회색(#222) 본문, 파란색 포인트 1색만. 각 슬라이드는 제목 한 줄 + 핵심 문장 1개 + 불릿 3~5개. 아래 `---` 가 슬라이드 경계다. 괄호 [ ] 안은 디자인 지시이고 본문에 넣지 말 것.

**슬라이드 3 · 과제가 정의한 문제**
RFP: 의뢰인은 "누가 적합한지, 얼마가 적정한지" 모르고 돈을 낸 뒤 결과물을 못 받을까 걱정한다. 프리랜서는 맞는 일을 찾기 어렵고 대금 미지급을 걱정한다.
- 과제가 제시한 해법: AI 단가 가이드 + 에스크로 결제 + 상호 평가

- 우리는 이 문제를 "건물 유지보수" 시장에서 다시 읽었다

**슬라이드 4 · 왜 건물 유지보수인가**
일반 프리랜서 매칭은 이미 닫힌 시장이다. 건물 보수는 아무도 안 보는 큰 시장이다.
- 숨고 누적 가입자 1,600만 명 — 경제활동인구의 절반, "안 써본 사람"이 없다
- 네이버 엑스퍼트(2024 종료), 사람인 긱(2025.9 폐쇄) — 트래픽으로도 못 버텼다
- 리모델링 공사의 97%가 비주거(상가·사무실). 기존 플랫폼은 전부 아파트 인테리어를 본다
- 전국 상업용 건물 142.7만 동, 30년 이상 노후 36%. 신축은 줄고(착공 −9.6%) 건물은 늙는다
[97% 와 142.7만 동을 큰 숫자로]

**슬라이드 5 · 연결만 하고 빠지면 죽는다**
2023~2025년 인테리어·시공 비교견적 서비스 7곳이 문을 닫았다.
- 하우스텝(투자 140억), 인스테리어, 집꾸미기, 알렛츠, 문고리닷컴, 어반베이스, 하우스앱

- 살아남은 곳은 하나를 더했다 — 오늘의집은 직접 시공, 위시켓은 대금 보호
- 결론: 분야를 좁히는 것만으론 부족하다. 신뢰 장치나 거래 방식을 바꿔야 산다

**슬라이드 6 · 진짜 문제는 가격이 아니라 범위다**

- 2025년 접수 795건, 전년 대비 44% 증가. 합의 없이 끝난 비율 64%
- 분쟁 이유: 하자보수 불만 57%, 계약 내용 미이행 25%. "추가 공사비" 분쟁은 2.8%뿐
- 95%가 "무엇을 하기로 했는가"의 분쟁이다. 원래 범위를 적은 문서가 없어서 하자를 판정할 기준이 없다
- 공정위 분쟁해결기준: "항목별 자재·단가·수량이 적힌 상세견적서는 계약서로 간주" — 제도는 이미 답을 써 놨다

**슬라이드 7 · 문제 정의와 우리의 해법**
소규모 건물 보수에는 "무엇을 하기로 했는가"를 항목 단위로 확정하는 문서가 없다.
- 해법: AI가 공사를 공정 단위로 한 번 쪼개고, 그 결과를 견적 → 계약서 범위 조항 → 작업 마일스톤 → 대금 지급 단위까지 끝까지 쓴다
- "한 번 쪼개고 끝까지 쓴다" — 따로 만들 기능 4개를 하나의 데이터로 꿰는 것이라 개발량이 늘지 않는다
- 겨냥하는 공포: 추가 공사비와 "이건 범위 밖" 분쟁
[중앙에 공정표 하나 → 네 갈래 화살표(견적·계약·마일스톤·정산) 다이어그램]

**슬라이드 11 · 데이터 모델 (ERD)**
18 테이블. RFP의 8개 엔티티를 기준으로 세 군데를 의도적으로 갈라냈다.
- 역할별 프로필 분리(client_profiles / freelancer_profiles): "프로필 미완성이면 입력 유도" 판정이 행 존재 여부 하나로 끝난다
- 프로젝트 상태 2축(recruit_status / deal_status): 외부 질의는 모집 상태만 본다
- scope_items 한 행 = 계약 범위 조항 = 마일스톤 = 정산 단위 — milestones 가 scope_items 를 직접 참조해 구조로 보장
- 계약 체결 시점의 공정표는 contracts.scope_snapshot(jsonb)에 사본으로 고정, 사후 변경 불가

**슬라이드 12 · API 설계 의도**
18 엔드포인트, 응답 봉투 한 모양: { ok, data } / { ok, code, message }
- 인증: Access(15분)/Refresh(14일) 토큰 직접 구현. Refresh 는 난수 + SHA-256 해시 저장, 사용 시 회전
- 프로필 미완성은 428 PROFILE_REQUIRED — 화면이 아니라 서버가 판정하고 돌아올 주소(next)를 같이 준다
- 수락은 트랜잭션 하나: 지원 accepted · 나머지 rejected · 프로젝트 closed+awaiting_contract · 알림 N건이 함께 바뀌거나 전부 안 바뀐다
- 수정 잠금도 서버가 판단: 지원자가 있으면 예산·마감일 변경은 409. 화면은 비활성화로 보여줄 뿐
- 알림 클릭은 GET /api/notifications/[id]/open → 읽음 처리 후 리다이렉트. 자바스크립트 없이도 동작
[엔드포인트 요약표 축약: 메서드·경로·역할 6~8줄]

**슬라이드 13 · 아키텍처와 도구 선택**
"작지만 완전한 제품"을 2주 안에. 선택 기준은 학습 목표를 건너뛰지 않는 것.
- Next.js 16 App Router + React 19 + Tailwind 4 — 화면과 API 를 한 레포, 한 배포로
- Prisma 6 + PostgreSQL(Neon, 싱가포르) — 트랜잭션·마이그레이션을 코드로 관리
- 자체 JWT: RFP 가 Access/Refresh 직접 구현을 요구해 Supabase Auth 등 관리형 인증은 쓰지 않았다
- 레이어: app/api(라우트) → lib/server(검증 zod·인증·where 빌더·알림) → prisma. 목록 조건 빌더는 API 와 화면이 공유해 결과가 어긋나지 않는다
- 배포 Vercel(함수 리전 sin1), 로컬은 Docker Postgres, 시간 경과 상태 전환은 크론 없이 "읽는 순간 맞춘다"
[좌: 레이어 다이어그램 3단, 우: 스택 로고 없이 텍스트 칩]

**슬라이드 15 · 검증 방식**
눈으로 클릭해 본 게 아니라 스크립트로 67개 검사를 돌렸다.

- 로컬 67/67, 프로덕션 67/67 통과. 기능을 올릴 때마다 같은 스크립트를 배포본에 다시 돌린다
- 테스트 데이터는 정리 스크립트로 제거해 시드 데모 계정만 남긴다
