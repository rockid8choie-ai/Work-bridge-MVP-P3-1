# 03. RFP (제안요청서)

> 과제 가이드 원문. 2026-10-13 사용자 전달분. 학습 플랫폼 UI 잔여물(접속자 수, 채팅 위젯 등)만 제거하고 내용은 그대로 옮김.

> 💡 본 RFP에 명시되지 않은 디테일은 팀 논의를 통해 자유롭게 추가하거나 결정해도 됩니다. 모호하거나 정의되지 않은 부분이 있다면 어떤 방향이 사용자와 비즈니스에 가장 적합할지 팀이 직접 고민하여 반영해 주세요. 단, 어떤 근거와 논리로 그 선택을 했는지 회의록, PR 설명, 스프린트 회고 등에 반드시 기록해 주시기 바랍니다. 실제 제품 개발 현장에서도 명세는 늘 불완전하며, 그 빈틈을 책임 있게 메우고 의사결정 과정을 문서화하는 것 자체가 중요한 학습이자 팀의 자산이 됩니다.

본 RFP의 요구사항은 다음 세 가지 우선순위로 이해해 주세요.

| 우선순위 | 내용 |
|---|---|
| **기본 필수** | 회원가입/로그인, 역할별 프로필, 프로젝트 CRUD, 검색/필터, 지원, 수락, 거절, 기본 알림 5종 등 서비스가 동작하기 위한 최소 기능 |
| **고급 필수** | AI 단가 분석, 계약서 생성과 서명, sandbox 결제 및 에스크로 정산, 상호 리뷰 등 차별화 가치를 만드는 기능 |
| **도전 과제 (선택)** | 다회차 금액 협상, 환불 처리, 고급 추천 알고리즘, 고급 알림 트리거, 관리자 정산 관리 등 시간적 여유가 있는 팀이 도전해볼 수 있는 영역 |

최종 결과물 평가는 기본 필수와 고급 필수를 기준으로 설계되어 있으며, 도전 과제는 더 깊이 있는 학습을 원하는 팀이 자율적으로 시도하는 영역입니다.

## 1. 프로젝트 배경 및 문제 정의

### 1.1 시장 배경

외주(프리랜서) 시장은 빠르게 성장하고 있으나, 의뢰인과 프리랜서 사이의 정보 비대칭이 크고 계약 및 대금 정산 과정에서 양측이 부담을 느끼는 영역입니다. 의뢰인은 어떤 프리랜서가 자신의 프로젝트에 적합한지 판단하기 어려워하며, 프리랜서는 본인의 역량과 단가에 맞는 프로젝트를 발견하는 데 어려움을 겪습니다. 계약 체결과 대금 지급 과정에서도 신뢰할 수 있는 중개 장치가 부재해 양측 모두 위험을 떠안고 거래하는 경우가 많습니다.

### 1.2 타겟 사용자

**의뢰인 (Client)**
- 외주 개발/디자인/마케팅 프로젝트를 의뢰하려는 개인 또는 기업 담당자
- 페인포인트: 적합한 프리랜서 발굴 어려움, 단가 산정의 막막함, 대금 지급 후 결과물 미수령 위험
- 기대: 검증된 프리랜서 풀, 합리적 예산 가이드, 안전한 거래 보호 장치

**프리랜서 (Freelancer)**
- 전문 분야(웹 개발, 디자인, 마케팅 등)를 가진 개인 프리랜서
- 페인포인트: 적합한 프로젝트 발견 어려움, 결제 지연 및 미지급 위험, 자신의 단가가 시장과 부합하는지에 대한 불확실성
- 기대: 본인 역량과 매칭되는 프로젝트 노출, 선결제 보장, 평판 축적 채널

### 1.3 비즈니스 목표

본 프로젝트는 위 페인포인트를 해결하기 위해 의뢰인과 프리랜서가 안전하게 연결되고 거래할 수 있는 양면형 마켓플레이스 MVP를 구축합니다. 핵심 차별화 요소는 다음 두 가지입니다.

1. AI 기반 단가 산정 가이드 — 의뢰인의 예산 책정 부담을 완화
2. 에스크로 결제 + 상호 평가 시스템 — 양측의 거래 신뢰를 확보

---

## 2. 주요 유저 시나리오

### 2.1 의뢰인 시나리오

1. 회원가입 후 의뢰인 역할로 진입한다. 첫 프로젝트 등록 시점에 의뢰인 프로필(회사명, 사업 분야 등) 입력을 안내받는다
2. 프로젝트를 등록한다 (제목, 설명, 카테고리, 일정, 예산, 필요 기술 스택). 예산 책정이 막막하면 AI 단가 분석을 호출해 도출된 단위 기능별 단가를 검토하고, 결과를 프로젝트 예산에 반영할 수 있다
3. 지원자를 검토해 한 명을 수락한다. 합의 금액을 확정하고 계약서를 양측 전자 서명으로 체결한 뒤, 전체 금액을 플랫폼에 에스크로 선결제한다
4. 프리랜서의 납품을 검토하고 완료 승인한다. 시스템이 수수료를 차감해 프리랜서에게 정산한다
5. 프리랜서를 평가한다 (별점, 텍스트, 태그)

### 2.2 프리랜서 시나리오

1. 회원가입 후 프리랜서 역할로 진입해 프로젝트를 탐색한다 (키워드, 카테고리, 예산, 기술, 마감일, 모집 상태 필터, 북마크 가능)
2. 마음에 드는 프로젝트에 지원한다. 첫 지원 시점에 프리랜서 프로필(활동 카테고리, 기술 스택, 경력, 단가, 포트폴리오) 입력을 안내받는다. 지원 직후 '내 지원 현황'에서 상태(검토중 / 수락 / 거절)를 추적한다
3. 수락 알림을 받으면 합의 금액에 동의/거부한다. 동의 시 양측 서명으로 계약이 체결되고, 의뢰인의 결제가 끝나면 작업을 시작한다. 완료 시 납품을 요청한다
4. 의뢰인의 완료 승인 후 정산받고, 의뢰인을 평가한다

### 2.3 거래 실패 시나리오

- **자동 거절**: 의뢰인이 다른 지원자를 수락하면 본 지원자는 자동 거절되며 '내 지원 현황'에 결과가 남는다
- **모집 마감**: 의뢰인이 모집을 마감하거나 마감일이 초과되면 미처리 지원은 일괄 거절되고 지원자 전원에게 알림이 발송된다
- **금액 합의 결렬**: 의뢰인이 수락한 후 제시한 합의 금액을 프리랜서가 거부하면 해당 지원은 '거절'로 처리되며, 프로젝트는 계약 체결 직전 단계(예: 모집 중)로 복귀해 다른 지원자를 받거나 의뢰인이 새 합의안을 제시할 수 있다. 이미 자동 거절된 다른 지원자는 복구하지 않는다 (권장 정책 — 다회차 협상, 거절 후 복구 등 대안은 팀 자율 설계 허용)
- **프로젝트 취소**: 계약 체결 이전 단계에서만 취소가 가능하며, 계약 체결 이후 단계에서는 정상 완료 또는 환불 흐름을 거쳐야 한다

## 3. 기능 요구사항

각 하위 섹션 제목 옆의 우선순위 라벨([기본 필수] / [고급 필수] / [도전 과제])과 아래 매트릭스로 영역을 한눈에 확인할 수 있습니다. 본 섹션의 세부 항목은 비즈니스 흐름이 자연스럽게 동작하도록 돕는 참고 가이드이며, 서비스의 핵심 동작만 보장한다면 화면, 세부 플로우 등 디테일한 부분은 팀이 자유롭게 설계해 주세요.

| 우선순위 | 영역 |
|---|---|
| 기본 필수 | 3.1 사용자 관리, 3.2 프로젝트 관리, 3.3.1 필수 알림 트리거, 3.3.2 알림 UI, 3.4 부가 기능 |
| 고급 필수 | 3.5 AI 단가 분석, 3.6 계약 및 결제, 3.7 리뷰 |
| 도전 과제 | 3.3.3 선택 알림 트리거, 3.6.4 환불 처리, 그 외 팀 자체 추가 기능 |

### 3.1 사용자 관리 [기본 필수]

#### 3.1.1 회원가입 및 로그인
- 이메일 기반 가입(이름, 이메일, 비밀번호, 역할 선택) 시 비밀번호는 해싱 저장하고 이메일 중복을 검증
- 로그인 시 Access Token과 Refresh Token을 발급하고, Access Token 만료 시 Refresh Token으로 자동 재발급
- 로그아웃 시 클라이언트에서 토큰을 삭제하며, 선택적으로 서버에서 Refresh Token을 무효화하는 엔드포인트 제공

#### 3.1.2 소셜 로그인 (OAuth 2.0)
- Google, Kakao 등 1종 이상의 소셜 로그인 제공
- 동일 이메일이 이미 가입된 경우 기존 계정과 연동
- 최초 소셜 로그인 시 역할 선택 페이지로 유도

#### 3.1.3 사용자 역할 및 프로필

모든 사용자는 의뢰인 또는 프리랜서 중 한 역할에 속합니다.

| 역할 | 프로필 필드 | 권한 |
|---|---|---|
| 공통 | 이름, 이메일, 프로필 이미지, 자기소개 | - |
| 의뢰인 | 회사명, 사업 분야(선택형, '기타' 자유 입력), 웹사이트 | 프로젝트 등록 권한 |
| 프리랜서 | 주요 활동 카테고리(선택형), 기술 스택(옵션 선택 + 커스텀 추가 허용), 경력(년수), 시간당 단가, 포트폴리오 URL | 프로젝트 지원 권한 |

**기술 스택 옵션 정리 지침**
다양한 기술 스택을 포괄하되, 너무 세분화된 옵션은 피하고 유사한 기술은 통합하여 관리합니다. (예: SQL로 통합하고 MySQL, PostgreSQL 개별 옵션 제거)

**프로필 완성 유도**
회원가입 직후 강제 입력은 없으며, 프로젝트 등록(의뢰인) 또는 지원(프리랜서) 액션 시점에 역할별 필수 프로필 정보가 비어 있으면 프로필 입력 페이지로 유도한 뒤 원래 액션으로 복귀시킵니다.

### 3.2 프로젝트 관리 [기본 필수]

#### 3.2.1 프로젝트 CRUD
- **등록 (의뢰인 전용)**: 3단계 입력 퍼널로 진행
  1. 기본 정보 (제목, 설명, 카테고리)
  2. 일정 및 예산 (모집 시작일, 마감일, 예산)
  3. 필요 기술 스택
- **수정**: 본인 프로젝트만 가능하며, 지원자가 있는 경우 예산/마감일 변경 제한
- **삭제**: 소프트 딜리트만 허용 (물리 삭제 금지)
- **상세 조회**: 프로젝트 정보 + 지원자 수 + 상태 + 하단 추천 프로젝트 섹션

#### 3.2.2 프로젝트 탐색
- 다중 진입 경로: 헤더 메뉴, 메인 페이지 검색창, 메인 페이지 카테고리 버튼
- 키워드 검색: 제목 및 설명 텍스트 검색
- 필터: 카테고리, 예산 범위, 필요 기술 스택, 마감일, 모집 상태(모집 예정 / 모집 중 / 마감)
- 정렬: 최신순, 마감임박순, 예산 높은순
- 페이지네이션: 페이지당 10개 (무한 스크롤 또는 번호형 모두 허용)

#### 3.2.3 프로젝트 상태 머신

프로젝트의 생애 주기는 크게 모집 단계(프리랜서가 지원할 수 있는 시기)와 거래 단계(계약 체결 이후의 거래 진행)로 나뉩니다.

**모집 단계**

| 상태 | 설명 | 전환 조건 |
|---|---|---|
| 모집 예정 | 모집 시작일 도래 전 | 등록 시점이 모집 시작일 이전일 때 |
| 모집 중 | 프리랜서 지원 가능 | 모집 시작일 도래 시 자동 전환 (시작일 미지정 또는 당일 등록 시 즉시 모집 중) |
| 모집 마감 | 더 이상 지원 불가 | 자동(마감일 초과), 수동(의뢰인 마감 처리), 또는 한 지원자 수락으로 거래 단계 진입 시 — 미처리 지원은 일괄 '거절' 처리 |

**거래 단계**

| 상태 | 설명 | 전환 조건 |
|---|---|---|
| 계약 대기 | 의뢰인의 수락은 끝났으나 금액 합의와 계약서 서명이 진행 중 | 의뢰인이 지원자를 수락한 직후 |
| 작업 중 | 계약 체결 및 의뢰인 결제 완료, 프리랜서가 작업 진행 | 양측 전자 서명 완료 + 에스크로 결제 완료 |
| 완료 | 납품 확인 및 정산 완료 | 의뢰인 완료 승인 + 시스템의 수수료 차감 후 지급 처리 |
| 취소 | 거래가 정상 진행되지 못하고 중단됨 | 계약 체결 이전 단계에서만 가능 (계약 체결 후에는 환불 흐름을 거쳐야 함) |

**외부 노출 규칙**
`/projects` 같은 외부 목록 화면에서는 모집 단계의 상태(모집 예정 / 모집 중 / 모집 마감)만 노출하며, 거래 단계로 진입한 프로젝트는 외부 목록에서 '모집 마감'으로 표시합니다. 거래 단계의 세부 상태는 의뢰인의 '내 프로젝트', 프리랜서의 '내 지원 현황', 계약서 상세 등 내부 화면에서만 노출합니다.

**구현 가이드 (자율 결정)**
- 위 구분은 사용자에게 보여줄 상태의 의미 모델이며, 데이터베이스에는 단일 상태 enum으로 둘지 모집 상태와 거래 상태를 별도 필드로 둘지 팀이 자유롭게 결정해도 됩니다. 단, 외부 노출 규칙과 전환 조건은 어느 방식으로 구현하든 동일하게 보장되어야 합니다.
- 거래 단계 세부 상태(계약 대기, 작업 중 등)를 더 세분화(예: '결제 대기'를 별도로 분리)하거나 통합하는 것도 팀 판단에 맡깁니다. 단, 결정 근거는 회의록 등에 기록해 주세요.

#### 3.2.4 지원 및 지원자 관리
- 프리랜서: 프로젝트에 지원서(자기소개, 예상 단가, 예상 기간) 제출 — 동일 프로젝트 중복 지원 방지
- 의뢰인: 지원자 목록 및 지원서 조회, 수락/거절 처리
- 자동 거절 (부수 효과): 한 지원자를 수락하면 동일 프로젝트의 다른 대기 지원자는 일괄 자동 '거절' 처리
- 자동 마감 처리 (부수 효과): 프로젝트가 '마감' 상태로 전환될 때 미처리 지원은 일괄 '거절' 처리
- 지원 현황 잔존: 수락/거절 처리 이후에도 '내 지원 현황'에 결과가 남아 프리랜서가 확인 가능해야 함
- 지원 완료 후 동선: 지원 제출 직후 '내 지원 현황' 페이지로 자동 이동

### 3.3 알림 시스템 [기본 필수] [도전 과제]

서비스 내 알림 센터로 사용자 간 상호작용을 전달합니다. 본 MVP에서는 인앱 알림만 구현합니다 (외부 채널 연동은 범위 외)

#### 3.3.1 필수 알림 트리거
아래 5종의 이벤트는 해당 수신자에게 알림을 보내고, 클릭 시 적절한 페이지로 이동시켜 주세요.
1. 프리랜서의 지원 → 의뢰인
2. 의뢰인의 지원 수락 → 해당 프리랜서
3. 타 지원 수락에 의한 자동 거절 → 거절된 프리랜서
4. 의뢰인의 직접 거절 → 해당 프리랜서
5. 의뢰인의 모집 마감 처리 → 지원자 전원

#### 3.3.2 알림 UI
- 미확인 알림이 헤더에서 즉시 식별 가능해야 하며, 알림 클릭 시 자동 읽음 처리
- 알림 목록 페이지에서 일괄 읽음 처리

#### 3.3.3 선택 알림 트리거 [도전 과제]
거래 단계 흐름을 풍부하게 하고 싶다면 아래 이벤트에 대한 알림을 추가로 구현할 수 있습니다.
- 합의 금액 동의/거부
- 계약 서명 완료
- 결제 완료
- 납품 요청
- 완료 승인
- 상호 평가 요청

### 3.4 부가 기능 [기본 필수]

#### 3.4.1 프로젝트 북마크 (프리랜서)
- 프로젝트 상세 페이지에서 북마크 토글 가능
- '내 북마크' 페이지에서 북마크한 프로젝트 모아보기
- 북마크 목록에서 프로젝트 상세 진입 및 지원 가능

#### 3.4.2 추천 프로젝트
- 프로젝트 상세 페이지 하단에 '추천 프로젝트' 섹션 노출
- 동일 카테고리 및 유사 기술 스택 기반의 단순 추천 (정교한 추천 알고리즘은 범위 외, 랜덤 수준 허용)

### 3.5 AI 단가 분석 [고급 필수]

의뢰인이 작성한 프로젝트 설명을 AI가 분석해 단위 기능별 및 전체 예상 단가를 산정하고, 의뢰인이 결과를 프로젝트 예산으로 반영할 수 있도록 돕습니다.

#### 3.5.1 분석 흐름
의뢰인의 분석 요청 → AI가 프로젝트 설명을 단위 기능 목록과 단가로 분해 → 리포트로 표시 → '예산 반영' 액션으로 결과를 프로젝트 예산 필드에 적용

#### 3.5.2 리포트 구성
- 단위 기능 목록 (기능명, 설명)
- 단위 기능별 예상 단가와 산정 근거
- 전체 예상 총 단가

### 3.6 계약 및 결제 [고급 필수] [도전 과제]

#### 3.6.1 금액 조율 및 계약서
- 프리랜서 제안 금액과 의뢰인 예상 금액이 다를 경우 양측이 합의 금액을 확정하고, 합의 후 계약서가 자동 생성(프로젝트명, 합의 금액, 기간, 양 당사자 정보 포함)되어 양측 전자 서명(체크박스 동의 허용)으로 체결됩니다. 체결된 계약서는 언제든 조회 가능합니다
- 권장 흐름: 의뢰인 수락 시 합의 금액 입력 → 프리랜서 동의/거부 → 합의 시 계약서 자동 생성. 다회차 협상, 채팅 기반 조율, 카운터 오퍼 등 더 자연스러운 UX 대안은 자유 설계 가능 — 합의된 금액이 계약서에 반영된다는 결과만 보장하면 됩니다

#### 3.6.2 결제 (PG 연동)
- 반드시 sandbox 환경에서 구현 (실결제 방지, 테스트 키는 환경 변수로 관리)
- 결제 요청 → PG 결제창 → 콜백 검증 흐름, 결제 내역 조회 페이지 제공

#### 3.6.3 에스크로 정산

| 단계 | 설명 | 처리 주체 |
|---|---|---|
| 1. 에스크로 결제 | 계약 체결 후 의뢰인이 전체 금액을 플랫폼에 선결제 | 의뢰인 |
| 2. 작업 진행 | 프리랜서가 작업 완료 후 납품 요청 | 프리랜서 |
| 3. 납품 확인 | 의뢰인이 납품물 검토 후 완료 승인 | 의뢰인 |
| 4. 대금 지급 | 플랫폼이 수수료(10%) 차감 후 프리랜서에게 지급 처리 (실제 이체는 미구현) | 시스템 |

납품 요청과 완료 승인은 별도 페이지를 신설하거나, 계약서 상세, 내 프로젝트, 프로젝트 상세 등 적절한 기존 화면에 액션 버튼으로 통합하는 등 팀이 자유롭게 화면 동선을 설계해 주세요.

#### 3.6.4 환불 처리 [도전 과제]
- MVP에서는 PG 환불 API 연동은 범위 외입니다. 결제 상태에 '환불'을 두되 실제 처리는 운영자의 수동 변경 수준으로 단순화하거나 시연 범위에서 제외해도 됩니다.
- 도전 과제로 진행하는 경우 sandbox 환불 API를 활용해 결제 → 환불까지의 상태 전환을 구현해 주세요.

### 3.7 리뷰 [고급 필수]

#### 3.7.1 상호 평가
- 프로젝트 완료 상태에서만 리뷰 작성 가능
- 의뢰인 → 프리랜서: 별점(1-5), 텍스트 리뷰, 태그 선택 (책임감, 소통, 기술력 등)
- 프리랜서 → 의뢰인: 별점(1-5), 텍스트 리뷰, 태그 선택 (명확한 요구사항, 신속한 피드백 등)
- 리뷰는 1회만 작성 가능하며 수정 불가
- 사용자 프로필에 평균 별점 및 리뷰 목록 표시

## 4. 데이터 모델 개요

핵심 도메인은 다음 엔티티로 표현할 수 있습니다. 엔티티의 분리, 통합, 명명, 관계 구조, 필드 정의는 팀 ERD 설계 단계에서 자유롭게 결정해도 됩니다.

- **User** — 의뢰인과 프리랜서를 통합 (역할 필드로 구분)
- **Project** — 의뢰인이 등록한 외주 프로젝트
- **Application** — 프리랜서의 지원서
- **Contract** — 계약서 (합의 금액, 양측 서명 정보)
- **Payment** — 결제와 정산 내역 (에스크로)
- **Review** — 의뢰인↔프리랜서 상호 평가
- **Notification** — 인앱 알림
- **Bookmark** — 프리랜서의 프로젝트 북마크

## 5. 외부 시스템 연동

- **OAuth 2.0 Provider** (Google, Kakao 등 1종 이상) — 소셜 로그인 인증, 동일 이메일은 기존 계정과 연동
- **LLM API** — 프로젝트 단가 분석, 구조화된 JSON 응답 파싱
- **PG (결제 게이트웨이)** — 결제 요청과 검증, 반드시 sandbox 사용, 키는 환경 변수로 관리
- **클라우드 스토리지** (1종 선택) — 이미지 업로드용, 접근 키는 환경 변수로 관리

## 6. 화면 구성

아래는 비즈니스 흐름을 커버하기 위한 참고용 화면 목록입니다. 화면 분리, 통합, URL 구조는 팀이 자유롭게 설계해 주세요.

- **기본 필수 화면**: 홈(랜딩), 프로젝트 목록, 상세, 등록/수정, 회원가입/로그인, 내 프로필, 사용자 공개 프로필, 지원 관리(의뢰인), 내 지원 현황(프리랜서), 내 프로젝트(의뢰인), 내 북마크(프리랜서), 알림 목록
- **고급 필수 화면**: AI 단가 분석 결과, 계약서 상세, 결제 페이지/결과, 결제 내역

## 7. 비기능 요구사항

### 7.1 보안
- 비밀번호는 반드시 해싱 저장하며 평문 노출 금지
- 모든 민감 정보(DB 접속 정보, JWT Secret, API Key 등)는 환경 변수로 분리하여 리포지토리에 노출 금지
- `.env.example` 파일을 리포지토리에 포함하여 필요한 환경 변수 목록 문서화
- 결제 연동은 sandbox 환경만 사용해 실결제 방지
- 본인 소유 리소스(프로젝트, 지원서, 계약서, 결제 등)에 대해서만 수정/조회 권한 부여

### 7.2 운영 및 배포
- 배포된 서비스 URL에서 회원가입 → 프로젝트 지원 → 계약 → 결제 → 리뷰까지 전체 시나리오가 실제로 동작해야 함
- 프론트엔드/백엔드 모두 GitHub 연동 자동 배포 환경 구성
- 시연 가능한 시드 데이터 확보 (배포된 서비스에서 즉시 동작을 확인할 수 있어야 함)

### 7.3 UX 원칙
- 주요 액션(등록, 지원, 결제 등) 후 사용자가 다음 단계로 자연스럽게 진입할 수 있는 동선 확보 (예: 지원 직후 '내 지원 현황' 자동 이동)
- 알림은 미확인 상태가 즉시 식별 가능하도록 표시
- 로그인 상태에 따라 헤더 메뉴 및 진입 동선이 명확히 구분되어야 함 (예: 로그인 전 '회원가입/로그인', 로그인 후 '내 프로필/내 프로젝트/알림' 등)
- 프로필 완성 유도 화면 같은 차단형 흐름은 원래 액션으로 복귀시키는 UX 보장

### 7.4 협업 및 산출물 운영
- Git 기반 협업: 브랜치 전략, 커밋 메시지 컨벤션, PR 리뷰 흐름 등은 팀에서 정의하여 일관성 있게 운영
- 칸반 보드 운영: GitHub Projects 또는 Notion 등 팀이 선택한 도구로 스프린트 단위 작업 관리
- 스프린트 계획서 및 회고록: 각 스프린트 단위로 작성

## 8. 수용 기준 (Acceptance Criteria)

각 스프린트 종료 시 아래 기준을 충족해야 합니다. 아래는 반드시 충족해야 하는 최소 기준이며, 팀이 자체적으로 추가하거나 변형한 기능 및 UX(예: 자체 설계한 금액 조율 흐름, 추가 화면 등)에 대해서는 그에 맞는 수용 기준을 별도로 정의해 함께 검증해 주세요.

### 8.1 스프린트 1과 2 종료 기준 [기본 필수]
- [ ] 이메일 및 소셜 로그인 모두 정상 동작
- [ ] 의뢰인 역할로 프로젝트 등록, 수정, 삭제, 상세 조회 가능
- [ ] 프리랜서 역할로 프로젝트 검색, 필터, 지원 가능
- [ ] 의뢰인의 지원 수락 시 타 지원 일괄 자동 거절 및 양측 알림 동작
- [ ] 프로젝트 상태가 시간 경과(모집 시작일과 마감일) 및 의뢰인 액션에 따라 올바르게 전환
- [ ] 5가지 알림 트리거가 정상 작동하고 헤더 미확인 표시가 노출
- [ ] 회원가입부터 프로젝트 지원, 알림 수신까지의 전체 플로우가 동작

### 8.2 스프린트 3과 4 종료 기준 [고급 필수]
- [ ] AI 단가 분석 요청 → 리포트 표시 → 예산 반영 흐름 동작
- [ ] 금액 조율부터 계약서 자동 생성, 양측 전자 서명까지 동작
- [ ] PG sandbox 결제 요청 → 콜백 → 검증 흐름 동작
- [ ] 에스크로 정산 흐름(선결제 → 납품 확인 → 수수료 차감 후 지급) 동작
- [ ] 프로젝트 완료 후 의뢰인 ↔ 프리랜서 상호 평가 작성 가능 및 평균 별점 노출
- [ ] 배포된 서비스 URL에서 위 전체 시나리오가 실제로 동작

### 8.3 도전 과제 종료 기준 [선택]

도전 과제는 필수 구현 항목이 아니며, 시간이 남거나 더 깊이 있는 학습을 원하는 팀이 자율적으로 선택해 진행합니다. 도전 과제를 진행하는 경우 아래 기준에 따라 동작을 검증해 주세요.

- [ ] 선택 알림 트리거 확장: 구현한 추가 트리거(합의 금액 동의/거부, 계약 서명 완료, 결제 완료, 납품 요청, 완료 승인, 리뷰 요청 등)가 의도한 시점에 발송되고 적절한 랜딩 페이지로 이동
