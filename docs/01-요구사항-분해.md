## 1. 제품 정의

**프리랜서 외주 매칭 플랫폼 — 버티컬은 건물 유지보수.**

- 의뢰인(Client) = **건물주**. 본인 건물의 보수·시공을 맡길 사람.
- 프리랜서(Freelancer) = **건물 유지보수 전문가**. 전기·설비·방수·인테리어 분야의 1인 기술자 또는 소규모 시공팀.

RFP는 프리랜서 분야를 "웹 개발, 디자인, 마케팅 등"으로 **예시**했을 뿐 한정하지 않는다.
건물 유지보수는 1인 기술자 비중이 높은 대표적 프리랜서 시장이므로 도메인 변경이 아니라 **카테고리 선택**이다.
엔티티·역할 구조는 RFP 그대로 두고(`client` / `freelancer`), 화면 문구만 건물주·전문가로 쓴다.

### 왜 이 버티컬인가

RFP 1.1이 지목한 문제는 정보 비대칭, 단가 산정의 막막함, **결과물 미수령 위험**이다.
건물 보수 시장에서 이 셋은 하나의 공포로 합쳐진다 — **"추가 공사비"**.

> 견적 300만원이라고 해서 맡겼는데, 뜯어보니 이것도 해야 한다며 끝나고 500만원을 요구한다.

가격이 아니라 **범위**가 분쟁의 원인이다. 이 프로젝트는 그 지점을 구조로 막는다.

## 2. 차별화 축 — 한 번 쪼개고 끝까지 쓴다

RFP의 고급 필수 세 항목(3.5 AI 단가 분석 / 3.6.1 계약서 / 3.6.3 에스크로)은
보통 서로 독립된 화면으로 구현된다. AI가 쪼갠 단위 작업은 리포트 화면을 벗어나는 순간 버려진다.

이 프로젝트는 **AI 분해 결과 1개를 네 곳에서 재사용**한다.

```
프로젝트 설명 ("3층 화장실 천장 누수, 아래층까지 번짐")
        │
        └─ AI 공정 분해 (1회)
             ├ 누수 원인 진단        18만원
             ├ 배관 교체             95만원
             ├ 방수 재시공          140만원
             └ 타일·마감 복구        67만원
                      │
      ┌───────────────┼───────────────┬──────────────────┐
      ▼               ▼               ▼                  ▼
  ① 예상 단가     ② 계약서의      ③ 작업 마일스톤    ④ 부분 정산 단위
     합계 320만    공사 범위 조항     (기성 단계)        단계 승인 시 지급
```

- **구현량이 늘지 않는다.** 전부 이미 필수 항목이다. 따로 만들 것을 하나로 꿰는 것이라 오히려 줄어든다.
- **업계 문서 형태와 일치한다.** 공사 견적서는 원래 항목·수량·단가 표다. AI 출력이 실제 견적서 모양이 된다.
- **기성고 정산이라는 실제 관행과 맞는다.** 공사비를 공정 단계별로 나눠 지급하는 건 건설업 표준이다.

**한 줄 포지셔닝 — "가격을 먼저 합의하지 않습니다. 범위를 먼저 합의합니다."**

## 4. 명세에 없어 직접 정한 것

RFP가 "모호한 부분은 근거를 기록하라"고 요구하므로 여기에 모은다.

| # | 빈틈 | 결정 | 근거 |
|---|---|---|---|
| D-01 | 프리랜서 분야가 열려 있음 | 건물 유지보수 버티컬로 한정 | 1인 기술자 비중이 높아 프리랜서 정의에 맞고, "추가 공사비" 분쟁이 RFP가 지목한 문제와 정확히 겹친다 |
| D-02 | AI 분석 결과의 사용처가 리포트까지만 명시됨 | 계약서 범위 조항·마일스톤·정산 단위로 재사용 | 분해 결과를 버리면 분쟁 예방 효과가 사라진다. 구현량을 늘리지 않고 제품 일관성을 얻는다 |
| D-03 | 프로젝트 상태를 단일 enum으로 둘지 분리할지 자율 | **분리** (`recruitStatus` + `dealStatus`) | 외부 목록에는 모집 단계만 노출해야 하는데, 단일 enum이면 조회마다 변환이 필요하다 |
| D-04 | 거래 단계 세분화 자율 | 계약대기 / 결제대기 / 작업중 / 완료 / 취소 | 서명 완료와 결제 완료 사이에 실제 대기 구간이 있고, 알림 트리거도 다르다 |
| D-05 | 금액 합의 방식 자율 | 1회 제시 → 동의/거부 (다회차 협상은 도전 과제) | 2주 일정에서 협상 UI는 비용 대비 효과가 낮다 |
| D-06 | 합의 결렬 시 자동 거절된 다른 지원자 복구 여부 | 복구하지 않음 (RFP 권장안 채택) | 복구하면 이미 발송된 거절 알림과 상태가 충돌한다 |
| D-07 | 기술 스택 옵션 입도 | 6개 대분류 (전기 / 설비·배관 / 방수·도장 / 인테리어·목공 / 소방·안전 / 공조·환기) + 커스텀 추가 | RFP의 "유사 기술은 통합" 지침 적용 |
| D-08 | 리뷰 태그 세트 | 전문가용 5종, 건물주용 5종 고정 | 자유 입력은 집계가 안 되어 평균 지표로 못 쓴다 |

### 1인 운영 방식

팀 프로젝트를 혼자 수행하므로 협업 산출물은 **1인 다역 운영 기록**으로 대체한다.

- 브랜치 전략: `main` ← `feat/*` · 직접 push 금지, PR 경유
- PR마다 **구현 의도와 판단 근거**를 본문에 기록 (RFP 요구사항)
- 셀프 코드 리뷰: 작성자 시점과 리뷰어 시점을 분리해 PR에 리뷰 코멘트를 남긴다
- 칸반: GitHub Projects, 스프린트 단위 운영
